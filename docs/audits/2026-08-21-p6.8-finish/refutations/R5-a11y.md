### R5-A1-6 — "22 of 24 grouped utterances are invisible on web"

**Verdict:** **MECHANISM WRONG, OBSERVATION HOLDS** — and it splits cleanly in two.
The **instrument** half is **CONFIRMED at full strength** and I am strengthening it. The **product**
half — *"Progress's headline number is announced by nothing at all on web"* — is **REFUTED as
stated**: **Chromium's own accessibility tree carries the name.** What the slice measured is
Playwright's snapshotter refusing to *report* the name, which is not the same thing as a browser
refusing to *expose* it.

**Platform:** **web only.** iOS is untouched, and that is settled from React Native's own native
source below, not inferred from the idiom's reputation.

#### Installed-source evidence

**1 — `accessible` really is dropped by RNW 0.21.2. CONFIRMED, three files deep.**

- `apps/rn/node_modules/react-native-web/src/modules/forwardedProps/index.js` — the key `accessible`
  appears in **neither** `defaultProps` (:10–22) nor `accessibilityProps` (:24–119). Every
  `accessibility*` sibling is in that list; `accessible` is not.
- `apps/rn/node_modules/react-native-web/src/exports/View/index.js:47` —
  `const pickProps = (props) => pick(props, forwardPropsList);` used at `:114`. An unlisted prop never
  reaches `createDOMProps` at all.
- `apps/rn/node_modules/react-native-web/src/modules/createDOMProps/index.js:44–154` — the destructure
  names ~90 props and `accessible` is absent there too, so even by the other route it would fall into
  `...domProps` unread rather than be interpreted.
- The role comes only from `AccessibilityUtil.propsToAriaRole` (`createDOMProps:163`;
  `propsToAriaRole.js:25–40`), which reads **only** `role` / `accessibilityRole`. No role prop → no
  `role` attribute → a bare `<div>`.
- The label does land: `createDOMProps/index.js:449–452` — `domProps['aria-label'] = _ariaLabel`.

So the emitted shape is exactly what the slice claims: `<div aria-label="…">`, role-less. ✅

**2 — Playwright cannot report that name, by construction. CONFIRMED.**

`node_modules/playwright-core/lib/coreBundle.js`, inside `getElementAccessibleName`:

```js
const elementProhibitsNaming = ["caption","code","definition","deletion","emphasis",
  "generic","insertion","mark","paragraph","presentation","strong","subscript",
  "suggestion","superscript","term","time"].includes(getAriaRole(element) || "");
if (!elementProhibitsNaming) { accessibleName = asFlatString(getTextAlternativeInternal(...)); }
```

A role-less `div` resolves to `generic`; `generic` is in the prohibit list; the accessible name is
hard-set to `""` **before `aria-label` is ever consulted.** Playwright implements the ARIA
name-from-prohibited rule *literally*. ⛔ **The nine trees in `p6.8-a11y/` therefore cannot show these
labels no matter what the browser does.**

**3 — ⚡ But Chromium does not implement that prohibition, and this is where the finding breaks.**

Measured, not reasoned. I built the four shapes as static HTML and dumped **both** trees from the
installed Chromium (`playwright-core` 1.60.0 / `chromium-1228`): Playwright's `ariaSnapshot()` and
Chromium's real AX tree via CDP `Accessibility.getFullAXTree`.

| shape rendered | Playwright `ariaSnapshot` | Chromium AX tree (CDP) |
|---|---|---|
| `<div aria-label="0% paid, …">` + `aria-hidden` children — *the exact ring shape* | **node absent entirely** | `generic  name="0% paid, no milestones reached yet, next milestone 25%"` |
| `<div aria-label="This paycheck $2,000, …">` + visible children — *PlanHero shape* | `- text: This paycheck$2,000` — label gone | `generic  name="This paycheck $2,000, …"` **plus** `StaticText "This paycheck"`, `StaticText "$2,000"` |
| `<div role="button" aria-label="Card, …">` | `- button "Card, …"` | `button  name="Card, …"` |
| `<div tabindex="0" aria-label="…">`, no role | `- text: inner c` — label gone | `generic  name="tabindex only, no role"  focusable=true` |

Pinned at `evidence/ax-probe.html`, `evidence/ax-probe.mjs`, `evidence/ax-probe-output.txt`.
Regenerate: `node docs/audits/2026-08-21-p6.8-finish/refutations/evidence/ax-probe.mjs
docs/audits/2026-08-21-p6.8-finish/refutations/evidence/ax-probe.html`.

**4 — iOS is unaffected, and this is source-decided.** The app runs the New Architecture
(`apps/rn/app.json:8` — `"newArchEnabled": true`), so the live path is Fabric:

- `apps/rn/node_modules/react-native/React/Fabric/Mounting/ComponentViews/View/RCTViewComponentView.mm:350`
  — `self.accessibilityElement.isAccessibilityElement = newViewProps.accessible;`
- Old architecture, for completeness:
  `apps/rn/node_modules/react-native/React/Views/RCTViewManager.m:177` —
  `RCT_REMAP_VIEW_PROPERTY(accessible, reactAccessibilityElement.isAccessibilityElement, BOOL)`
- `RCTViewComponentView.mm:1402–1413` — `accessibilityLabel` returns `super.accessibilityLabel` when
  one is set, else recurses the subtree. `accessible` + `accessibilityLabel` is therefore exactly the
  one-element-with-an-explicit-name idiom, and it is wired.

#### What this changes, precisely

1. **The instrument claim stands, and gets stronger.** ⛔ The `p6.8-a11y` dumps under-report every
   role-less grouping in this app, and **no lens may read a run-on `- text:` node as "this row is one
   unreadable string."** A1-6's most consequential sentence is right. The cause, though, is not
   "ARIA forbids it" — it is **the snapshotter's own hard-coded prohibit list**, a property of the
   tool. That matters because it means the blindness is *permanent for this instrument*: no app-side
   change short of adding a role will make these labels appear in an `ariaSnapshot`, so a future
   re-capture showing the same run-on nodes proves nothing.
2. **The stated mechanism is wrong.** *"ARIA forbids a `generic` from carrying a name [so the label
   vanishes]"* describes the spec and Playwright, **not the browser**. This is portfolio law IV
   arriving on schedule: a finding that came with a mechanism, whose recommendation is sound and
   whose mechanism is not.
3. **⛔ "Progress's headline number is announced by nothing at all on web" is REFUTED.** The name is
   present in the tree a web screen reader consumes. The residual risk is real but *different and
   smaller*: a **named `generic` whose content is `aria-hidden`** is a node most ATs do not stop on in
   browse mode, so the name may be present-but-never-visited. That is an unmeasured AT-behaviour
   question and it cannot be settled by any tree dump, Playwright's or Chromium's.
4. **⚡ A defect the slice missed, arriving from the same measurement.** On the PlanHero shape Chromium
   exposes the composed name **and** the child `StaticText` fragments — nothing collapses the subtree
   on web. So web is not "the label is lost"; it is **"the label and the fragments are both there"** —
   the exact double utterance the grouping was written to prevent, arriving from the other direction.
   Only the sites that additionally fence their children with `{...decorative}` (the ring,
   `progress.tsx:167`) lose content rather than duplicate it. **The web fix is therefore not "add a
   role" everywhere** — a role alone would leave the duplication in place at ~19 of the 20 sites.

from source at `ae80a88` by token-level scan with comments excluded:

→ **20 role-less of 23**, not 22 of 24. ⚠️ `TrajectoryChart.tsx` is under `src/components/payoff/`,
not `src/components/progress/` as the slice's list says. Immaterial to the finding; material to

**Already covered by a gate?** **No, and correctly so.**
`scripts/check-native-a11y-props.ts` bans a fixed set of four native-only props
(`accessibilityElementsHidden|importantForAccessibility|accessibilityState|accessibilityValue`) — a
different asymmetry, and `accessible` is not in it. `scripts/check-a11y-collapse.ts` fires only on an

**Residual doubt**

- The probe is static HTML built to the shape RNW emits, not the running web bundle. It proves what

- WebKit/Safari was not probed, and the public embed's Safari share is not zero.
- The `RCTViewComponentView.mm` reading is of the shipped ObjC in `node_modules`, not of a running
  app. It establishes the wiring exists; it does not establish VoiceOver's traversal. §A1.1 still owes.

### R5-A1-2 — the cushion bars announce the engine's token, not the shipped words

*(the brief calls this A1-5; see the numbering note above)*

**Verdict:** **CONFIRMED (both platforms)** — and the fix is smaller than the slice says, because the
correct value is already sitting in the same object.

**Platform:** **both.** The string is literal in source, so it is emitted identically by both renderers.
Where they differ is only in *who can hear it*: on **iOS** it is certainly spoken (`accessible` →
`isAccessibilityElement`, explicit label). On **web** it lands as `aria-label` on a role-less `div` —
absent from Playwright's dump (which is why `progress.txt` reports "Guardian-band words present: 0")
but **present in Chromium's AX tree** per R5-A1-6. So web is "possibly spoken", not "safe".

**Installed-source evidence**

- `apps/rn/src/components/progress/CashFlowSection.tsx:132–135` — the label interpolates the raw token:
  ```tsx
  <View style={styles.col} accessible
    accessibilityLabel={`${shortDate(cycle.cycleStart)}: ${formatWhole(cycle.net)} of room, ${cycle.cushionStatus}`}>
  ```
- `packages/core/timeline/buildMultiCycleTimeline.ts:18–20` — the token set, and where it comes from:
  ```ts
  export function toCushionStatus(state: GuardianState): CushionStatus {
      return state === "clear" ? "stable" : state === "tight" ? "tight" : "pressure";
  }
  ```
- `packages/core/copy/vocabulary.ts:132–136` — the shipped words are `Clear` / `Tight` / `Very tight`.
- `apps/rn/src/store/glossary.test.ts:26–33` — the gate asserts on `GUARDIAN_STATE_LABEL` **only**. It
  never imports a component (its own header says why: *"this runner is plain `tsx`"*). ✅ The slice's
  claim that the gate reads the constant and not the label is exactly right.
- `apps/rn/src/components/plan/CashRunwayChart.tsx:44, 167` — the positive control, and it is one line:
  `const STATE_LABEL = GUARDIAN_STATE_LABEL;` … `accessibilityLabel={\`${shortDate(...)}, ${STATE_LABEL[cycles[i].guardianState]}\`}`.
  That is why `cushion-forecast.txt` shows seven band words and `progress.txt` shows none.

**⚡ What the slice missed, and it makes the finding cheaper to close.** `TimelineCycle` carries
**both** fields — `buildMultiCycleTimeline.ts:28–31`:

```ts
cushionStatus: CushionStatus;
/** The canonical unified Guardian band for this cycle (§2.2 / round-4 F4). `cushionStatus` is its
 *  display alias. Driven by floor-relative headroom (`net`), NOT `endingBalance`. */
guardianState: GuardianState;
```

So `CushionBar` already has `cycle.guardianState` in hand; the fix is
`GUARDIAN_STATE_LABEL[cycle.guardianState]`, identical to `CashRunwayChart`. ⚠️ And note the comment
is **inverted against the code it documents**: it calls `cushionStatus` the *display alias* when
`guardianState` is what every displayed word is keyed off. That inversion is plausibly how this defect
was written in the first place — an author reading that comment would reach for `cushionStatus`.

**Already covered by a gate?** **No.** `glossary.test.ts` pins the constant, `a11y-axe.spec.ts`'s rule
set is `['aria-hidden-focus','aria-hidden-body','aria-valid-attr-value','aria-required-children']` —
none of which has an opinion about vocabulary — and neither `check-native-a11y-props.ts` nor
`check-a11y-collapse.ts` reads label *contents*. Nothing in the repo compares a spoken string against
the shipped glossary.

**Residual doubt** — none on the string. The only open question is A1-3's: the default seed never
produces a `pressure` cycle, so the two *worst* words have never been rendered by anything. That
strengthens rather than weakens the finding: the words a user would hear at their worst moment are the
ones with zero coverage.

### R5-A1-7 — `ListRow`'s swipe-delete is permanently in the tree, announced before the row

**Verdict:** **CONFIRMED (web)** for the tree/tab-order defect. **iOS: genuinely undecided**, and the
slice is right to route it to a device row rather than reason about it.
⚠️ **One clause of the claim is wrong**, and it matters for whoever writes the fix — see below.

**Platform:** **web confirmed** from the captured tree; **iOS unknown**. On iOS the pane is translated
outside its `overflow: hidden` container and whether UIAccessibility returns it is not decidable from
source. There is also a mitigation on iOS that does not exist on web: `RowContextMenu`
(`ListRow.tsx:165`) supplies a long-press Delete, so iOS has a reachable non-swipe path regardless.

**Installed-source evidence**

- `apps/rn/src/components/ui/ListRow.tsx:141–149` — `renderRightActions` returns a bare `Pressable`
  with `accessibilityRole="button"` and `accessibilityLabel={\`Delete ${title}\`}`. **No `a11yHidden`,
  no `useInert`, no `open` state.** The component holds no open/closed state at all — `swipeRef` is
  its only handle.
- `apps/rn/src/components/ui/ListRow.tsx:158–168` — `renderRightActions` is passed to
  `ReanimatedSwipeable` unconditionally whenever `onDelete` is set, and the pane mounts with the row.
- `apps/rn/capture-ref/p6.8-a11y/money.txt:19–20` — the order is as claimed, delete first:
  ```
  - button "Delete Card": Delete
  - button "Card, $5,000 · 20% APR, verified, $100/mo": Card Focus $5,000 · 20% APR verified $100/mo
  ```
- The counter-example is real: `apps/rn/src/components/plan/RequiredActionsCard.tsx:222–239` —
  `SwipeMarkAction` does `useInert(ref, !open)` **and** `{...a11yHidden(!open)}`, driven by `open`
  state that `RequiredRowView` maintains via `onSwipeableWillOpen` / `onSwipeableWillClose` (`:355–357`).
- `apps/rn/src/hooks/use-inert.ts:21–29` — `useInert` is **web-only** (`if (Platform.OS !== 'web')
  return;`). So the guard the slice wants copied is half a web fix; `a11yHidden` is the cross-platform
  half.

**⚠️ The clause that is wrong.** The slice quotes `RequiredActionsCard`'s comment as the rule and
treats the two as the same design. They are not. That comment (`:335–342`) states the pane is *"hidden
from the a11y tree **PERMANENTLY** rather than only while closed,"* and gives as reason (2) that
*"gating it on open/closed needs component state, and re-rendering during the open animation resets
`ReanimatedSwipeable`'s pan — the row snaps shut the instant it opens. That was measured here, not
assumed."* **The shipped code does exactly the thing the comment says was measured and rejected** —
`a11yHidden(!open)` with `open` in React state. Either the comment is stale or the measured failure
was fixed and the comment was not updated. ⛔ This matters directly: a fix for `ListRow` copied from
`RequiredActionsCard` inherits an animation-reset risk that the code's own documentation says was
observed. **Resolve which is true before copying the pattern.** Filed as a new finding, R5-N1.

**Already covered by a gate?** **No, and the slice's reason is right for a better reason than it
gives.** `a11y-axe.spec.ts:19` runs only
`['aria-hidden-focus','aria-hidden-body','aria-valid-attr-value','aria-required-children']`. A visible,
non-hidden, focusable Delete button violates none of them — `aria-hidden-focus` needs an
`aria-hidden` ancestor to fire at all. `check-a11y-collapse.ts` looks for the opposite shape (a
Pressable *inside* an `accessible` wrapper). Nothing covers "a control that should not be reachable
yet."

**Residual doubt**
- Whether iOS VoiceOver reaches an off-screen swipe pane. Undecidable from source; §A1.4 owes it.
- Severity is correctly hedged by the slice: the control is *named* (`Delete Card`, not a bare
  "Delete") and `confirmDelete` gates the write (`ListRow.tsx:135–139`). Bad order and a stray tab
  stop, not silent data loss.

### R5-A1-8 — `groupLabel` drops `badges`, so **Focus** reaches nobody

**Verdict:** **CONFIRMED (both platforms)**, and **UNDERCOUNTED** — there is a third dropped badge the
slice does not list, and it is one the code deliberately designed.

**Platform:** **both**, by two different mechanisms, which is why the fix has to be at the label:
- **iOS** — `groupLabel` emits `accessible: true` + an explicit `accessibilityLabel`, and
  `RCTViewComponentView.mm:1402–1407` returns `super.accessibilityLabel` when one is set *instead of*
  recursing the subtree. The badge text is unreachable.
- **web** — the badge text survives as `StaticText` inside the element (visible in `money.txt:20`
  after the colon, and in my Chromium probe), but the element is `role="button"` with an `aria-label`,
  so its computed **name** wins and its children are not separately navigated. Effectively dropped.

**Installed-source evidence**

- `apps/rn/src/utils/a11y.ts:19–27` — `groupLabel(...parts)` takes strings only; `badges` is a
  `ReactNode` and is not a parameter.
- `apps/rn/src/components/ui/ListRow.tsx:72` —
  `groupLabel(title, [meta, caption].filter(Boolean).join(', ') || undefined, amount ? ... : undefined)`.
  `badges` (`:91`, rendered inside `styles.titleRow`) is never consulted.
- `apps/rn/capture-ref/p6.8-a11y/money.txt:20` — name vs content, on one line:
  `name: "Card, $5,000 · 20% APR, verified, $100/mo"` against content `Card Focus $5,000 · 20% APR verified $100/mo`.

**⚡ The third dropped badge.** `apps/rn/src/app/(tabs)/money.tsx:483–486`:

```tsx
const chips = [
  focus ? <Pill key="f" label="Focus" tone="action" /> : null,
  isBnpl ? <Pill key="b" label={debt.bnplProvider || 'BNPL'} tone="neutral" />
         : debt.isAutopay ? <Pill key="a" label="Autopay" tone="autopay" /> : null,
].filter(Boolean);
```

For a BNPL debt the second chip is the **provider name** — and `meta` for that row is
`"${balanceText} · N of M paid · interest-free"` (`:478–482`), which never names the provider. The
comment at `:473` states the intent outright: *"the pill names the provider (2.7.3)."* So a
screen-reader user is told *"Klarna, 2 of 4 paid, interest-free"* minus the word Klarna — and unlike
Focus/Autopay this one is a **named product decision** being silently undone. The dropped set is
therefore **Focus · Autopay · the BNPL provider name**, not two items.

**The slice's refutation of the other two callers holds** — I checked both rather than accepting them:
Goals' `Funded` badge (`money.tsx:963`) is redundant with `amountSuffix={funded ? ' saved' : ' left'}`
(`:962`), and Living-expenses' `Off` badge (`living-expenses.tsx:71`) is redundant with
`meta={item.enabled ? 'Counts toward reserve' : 'Not counted'}` (`:69`). ⚠️ Line-number drift to carry
forward: the slice cites `money.tsx:485–486, 763, 961` and the actual `badges=` props are at
**`:496`, `:763`, `:963`**, with the chip construction at `:483–486`; `living-expenses.tsx:71`, not `:69`.

**Already covered by a gate?** **No.** No gate compares an accessible name against rendered content;
`check-a11y-collapse.ts` is the only script that even looks at `accessible`, and it asks a structural
question, not a completeness one.

**Residual doubt** — none material. The `ReactNode` signature makes this decidable from source, and
both platform mechanisms are read from installed source. The only unknown is whether iOS VoiceOver
users would *prefer* the badge before or after the amount, which is a copy question for §A1.5.

### R5-A1-10 — the app's only live region is `@platform android`

**Verdict:** **CONFIRMED (iOS only)** as a defect — and **INCOMPLETE**. The slice found half of a

  ```js
  announceForAccessibility: function (announcement: string): void {},
  ```
  An empty function body. `apps/rn/src/utils/a11y.ts:136–139`'s `announce()` calls straight into it, so
  **every `announce()` in this app does nothing on web** — which the repo already half-knew
  (`src/store/tutorialPath.test.ts:87,117` says so in comments) but which the slice does not connect
  to A1-10. The consequence is the finding's real shape:

  | | iOS | web |
  |---|---|---|
  | `accessibilityLiveRegion` / `aria-live` | ⛔ dropped (`@platform android`) | ✅ works |
  | `announce()` → `announceForAccessibility` | ✅ works | ⛔ no-op |

  ⛔ **There is no single primitive in this codebase that announces on both platforms.** Any fix for
  A1-9 or A1-10 must use *both*, or add a cross-platform helper to `a11y.ts` — which is exactly the
  "one rule in one place" shape that file exists to hold. That is the finding, and it is bigger and
  more actionable than "iOS is silent."

- **The callsite audit holds.** Enumerated at `ae80a88`, `announce()` fires at 6 sites and **all 6 are
  tutorial / demo / screen-title**: `app/(tabs)/index.tsx:867` and `:972` are both inside the tutorial
  **sandbox** subtree (`useStore(sandbox, …)`, beat 3 and beat 4 payoffs — see the `[C2]` comments at
  `:845` and `:958`), `TutorialOverlay.tsx:57`, `demo.tsx:76`, `cushion-forecast.tsx:33` and
  `schedule/[id].tsx:26` are screen-title announcements. ✅ **Zero fire in the ordinary app.** I
  checked `index.tsx:867/972` specifically because they are the two that look ordinary from the path;
  they are not.

**Already covered by a gate?** **No.** `check-native-a11y-props.ts`'s `BANNED` list is
`accessibilityElementsHidden|importantForAccessibility|accessibilityState|accessibilityValue` — a
platform asymmetry running the *other* direction (native-only props dropped by web). ⚡ **This is the
same class of defect as the one that script exists to catch, arriving from the opposite side, and the
script has no room for it** — its premise is "web drops native props", and `accessibilityLiveRegion`
is the case where *iOS* drops one. Worth saying plainly, because "we have a guard for this class" is
the assumption that would let it ship.

**Residual doubt**
- Whether `accessibilityRole="alert"` auto-announces under iOS VoiceOver is asserted by the slice and
  is **not** settled from source here. RN maps roles to `UIAccessibilityTraits`; there is no
  `UIAccessibilityTraitAlert`, and no `UIAccessibilityPostNotification` call in the View path — which
  supports the slice — but "supports" is not "measured". §A1.3(d) owes it.
- Whether the save-failure state is even reachable on a device to test. `storageError === 'save-failed'`
  needs a real write failure; the §A1.3(d) row already hedges with "if reachable".

### R5-A1-11 — `aria-selected` on `role="button"` on the paywall

**Verdict:** **CONFIRMED (web only)** — and **UNDERCOUNTED by 5 sites**, one class of which is
**worse than the slice's**: it does not drop the state, it **inverts** it.

**Platform:** **web only**, and both halves are now measured rather than reasoned.

**Installed-source evidence**
- `apps/rn/src/app/paywall.tsx:310–316` — `<Pressable accessibilityRole="button" {...a11ySelected(isSel)}
  accessibilityLabel={…}>`. Confirmed verbatim.
- `apps/rn/src/utils/a11y.ts:106–110` — the docstring predicts it, exactly as the slice says:
  *"`aria-selected` is only valid on a handful of roles (`tab`, `option`, `row`, `gridcell`,
  `treeitem`). On a plain `role="button"` it is ignored by assistive tech … This helper does not choose
  for the caller."*
- **Web, measured** (`evidence/ax-probe2-output.txt`): `<div role="button" aria-selected="true">` →
  Chromium AX gives `button  name="Annual, Best value"  props=focusable=true`. **No `selected`
  property at all.** Not "ignored by some AT" — not present in the tree. ✅ Confirmed hard.
- **iOS, from source** — the slice's mitigation is right and now has a citation:
  `react-native/Libraries/Components/Pressable/Pressable.js:227–232` —
  `let _accessibilityState = { … selected: ariaSelected ?? accessibilityState?.selected }`, and
  `React/Fabric/Mounting/ComponentViews/View/RCTViewComponentView.mm:429–432` —
  `if (accessibilityState.selected) { self.accessibilityTraits |= UIAccessibilityTraitSelected; }`.
  So iOS announces "selected". **Web only.** ✅

**⚡ The undercount, and it is the more serious half.** `a11ySelected` is used at **6** sites, not 1:

| site | role | web result (measured) |
|---|---|---|
| `app/paywall.tsx:314` | `button` | state **absent** |
| `components/payday/PaydayCaptureSheet.tsx:254` | `button` | state **absent** |
| `components/payday/PaydayCaptureSheet.tsx:397` | `button` | state **absent** |
| `components/ui/RadioGroup.tsx:28` | **`radio`** | ⛔ `checked="false"` — **inverted** |
| `components/plan/SaveForItSheet.tsx:118` | **`radio`** | ⛔ `checked="false"` — **inverted** |
| `components/plan/SaveForItSheet.tsx:141` | **`radio`** | ⛔ `checked="false"` — **inverted** |

`aria-selected` is not valid on `radio` either — `radio` takes `aria-checked` — and `a11y.ts`'s own
list of valid roles does not include it. Measured (`evidence/ax-probe2.html` shape B):
`radio  name="Every two weeks"  props=focusable=true,checked="false"`. **Chromium supplies the
default `checked="false"`, so the chosen option is announced as NOT chosen.** ⛔ That is a
worse-than-silence defect and it is on the pay-cycle picker and the save-for-it option list. Three
sites, none of them the paywall, none of them in the slice.

The correct pattern already exists two files away: `components/ui/SegmentedToggle.tsx:60,75–76` —
`accessibilityRole="radiogroup"` wrapping `accessibilityRole="radio"` + `a11yChecked(active)`. My
probe confirms it: `radio  name="Debts"  props=focusable=true,checked="true"`. ⚠️ `RadioGroup.tsx:20`
and `SaveForItSheet` also lack the `radiogroup` wrapper `SegmentedToggle` has — a second, smaller
delta from the same reference component.

**Already covered by a gate?** **No — and the near-miss is worth recording.** `a11y-axe.spec.ts:19`
runs `['aria-hidden-focus','aria-hidden-body','aria-valid-attr-value','aria-required-children']`.
`aria-valid-attr-value` checks that an attribute's *value* is well-formed — `"true"` is a valid value
for `aria-selected` — and has no opinion about whether the attribute is permitted on the role. **The
rule that catches this is `aria-allowed-attr`, and it is not in the list.**

⭐ **Measured, not assumed.** Running the installed `axe-core` over `evidence/ax-probe2.html` with
`runOnly: ['aria-allowed-attr','aria-valid-attr-value']` (`evidence/axe-rule-probe.mjs`,
`evidence/axe-rule-probe-output.txt`):

```
VIOLATION aria-allowed-attr -> <div role="button" … aria-selected="true" …> | <div role="radio" … aria-selected="true" …>
```

`aria-allowed-attr` flags **both** shapes; `aria-valid-attr-value` flags **neither**. So adding one
string to `a11y-axe.spec.ts:19` gates all six sites. Nothing else in the repo looks at role/attribute
compatibility;
`check-native-a11y-props.ts` bans a fixed prop list, and `a11ySelected`'s docstring explicitly
declines to choose.

**Residual doubt**
- The `radio` inversion is measured on the raw markup shape, not on the running app. RNW emits
  `role` and `aria-selected` verbatim (`createDOMProps:654–657, 724–728`), so the shape is right, but
  a DOM dump from the real build would close it.
- Whether iOS VoiceOver announces a `radio` with `TraitSelected` sensibly (vs. a `checked` value) is
  not settled here. The three `radio` sites are safe-ish on iOS by the same aliasing as the paywall,
  but "announces something" is not "announces the right thing".
- The paywall mitigation the slice cites is real: the CTA restates the choice
  (`Start Premium — $29.99 per year`, in `paywall.txt:14`). The three `radio` sites have no such
  restatement.

### R5-N1 — `RequiredActionsCard`'s comment documents a design the code does not implement

**Severity:** minor *(a documentation defect — but it sits on the fix path for A1-7, which is why it

### R5-N2 — `useInert` is web-only, so half of the A1-7 remedy does not exist on iOS

### R5-N3 — `cushionStatus`'s doc comment inverts its own relationship to `guardianState`

`GUARDIAN_STATE_LABEL`. An author following that comment reaches for the wrong field — which is
plausibly how A1-2 was written. One-line fix; filed because the comment will otherwise reproduce the
defect.
