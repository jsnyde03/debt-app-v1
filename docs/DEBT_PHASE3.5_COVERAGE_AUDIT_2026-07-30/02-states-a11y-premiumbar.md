# Lens 2 — Guardian-state / path coverage · the tutorial & demo as premium + accessible artifacts · coach-mark completeness

**VERDICT: GAPS FOUND — the spec is a strong skeleton with three structural holes: (1) interactive-accessibility is one un-specced word ("a11y verify") on a feature whose core interactions (drag-a-slider · tap-zones · watch-it-animate) are exactly the ones VoiceOver cannot operate by default; (2) the tutorial's state coverage never names its states — it teaches tight-ish mechanics but skips the flagship shortfall/Recovery state entirely and has no explicit exclusion list for missed-paycheck/graduation; (3) the path layer (skip · resume · demo-exit · first-fire timing · (A)/(C)/onboarding sequencing) is almost entirely unwritten. All fixable pre-build; none invalidates the design.**

Audited against: `DEBT_ELEVATION_PLAN.md` §Phase 3.5 (A)/(B)/(C) + ▶ NOW · Guardian states as shipped (`computeState` = `clear | tight | at-risk`, plus the distinct shortfall/Recovery, missed-paycheck/paused-deploy (§2.3.1), stale, debt-free/graduation (§2.7), and the free-tier read — the RS.6 e2e harness already scripts **all** of these: `guardian.spec.ts` covers "at-risk · missed/paused · stale · debt-free→savings + clear/tight/shortfall/free/intro") · `src/utils/a11y.ts` (WCAG 2.2 AA standard) · `src/data/demoSeed.ts` (existing `isDemoMode`) · the Phase-3 motion/celebration patterns (`theme/motion.ts`, 21 files already reduce-motion-aware).

---

## 1. State coverage

**What the spec exercises today.** Tutorial (A): an implicit tight-ish state ("will you make it this paycheck?" + a safe move), the bar zones, floor-drag re-plan, reserve absorb→release. Demo (B): tight one-tap · floor auto-protect · water-fill · scorecard-as-preview · reserves HELD · a free at-risk showcase. Nowhere does either name which `GuardianState` the sandbox sits in at each step.

- **GAP S1 — the state *transition* is the lesson, and it isn't specced.** The whole point of "drag the floor, watch it re-plan live" is watching the Guardian *change its mind*. The spec never says the drag should cross state boundaries. If the sandbox is tuned so the slider sweeps **clear → tight → at-risk and back**, the user learns the state model (colors, voice, hysteresis) by *causing* it — the single highest-value teach in the feature. If it's tuned to stay inside one band, the flagship interaction teaches only "numbers move."
  **REC:** spec the sandbox numbers so the floor-drag range provably crosses all three `computeState` bands; each crossing gets the real state visual + one line of the real state voice. (Hysteresis: decide whether the tutorial shows it or the sandbox disables it for legibility — either is fine, but decide.)
- **GAP S2 — shortfall/Recovery is absent from the tutorial.** The Recovery Plan is the declared **top differentiator** (2.6, "the last Guardian piece") and the scariest moment a real user will hit — and the tutorial's step list never shows a deficit or the COVER NOW / SAFE-TO-DEFER ladder. First contact with Recovery will be a real crisis, untaught.
  **REC (pick one, explicitly):** (a) add a short optional step ("what if it doesn't fit? → watch me build the recovery ladder" on the sandbox) — recommended, it's the moat; or (b) deliberately exclude it from the tutorial and spec a **contextual first-shortfall micro-intro** (one calm coach-mark-style beat the first time the real Recovery section renders). Silence is the only wrong option.
- **GAP S3 — no explicit exclusion list.** Missed-paycheck/paused-deploy, stale/verify-soon, graduation/debt-free are (reasonably) not tutorial material — but the spec doesn't *say* they're excluded or where they ARE taught. Un-stated exclusions read as accidental gaps in every later audit.
  **REC:** add a one-line coverage table to the (A) spec: state → taught in tutorial / taught contextually in-situ (paused-deploy + graduation already self-narrate on the real card) / not taught. The RS.6 harness state list is the checklist — reuse it verbatim.
- **GAP S4 — free-vs-premium contrast is half-specced.** (B) has the "free at-risk showcase state," good. But: (i) **where does it live** — inside the demo as a toggle? a paywall deep-link? un-specced; (ii) the **tutorial** fires on *first premium* Guardian view only — the free tier's honest read gets no tour and the "?" entry isn't specced for the free card. A free user tapping "?" is a value-led premium moment (the tutorial itself can be the taste, per [[feedback_premium_gating_value_led]]) — or a dead end. Un-specced which.
  **REC:** spec the free-card "?" behavior (recommended: free users CAN run the tutorial — it's the best paywall the app has; the premium-only bits render as the invitation, never blurred) and pin the free-at-risk showcase's entry point + its side-by-side/toggle mechanic for the contrast.
- **GAP S5 — tutorial reserve-release vs demo honesty tension, unreconciled.** (A) shows "once I've learned you → watch it release"; (B)'s hard rule is reserves HELD, never a matured Guardian. Same sandbox, opposite beats. Fine — teaching future behavior isn't promising it — but only if the tutorial's release step carries the time-honest frame ("this is what happens *after a few cycles*, not day one"). Not specced.
  **REC:** one spec line: the release step's copy is future-framed, and the demo script never reuses that step.
- **GAP S6 — sandbox income shape un-specced.** Fixed vs variable income changes what renders (band/cone · lean · scorecard promise). The demo's "once I learn your income" implies variable; the tutorial doesn't say.
  **REC:** pin it (recommended: variable — it exercises the richer premium surface and matches the scorecard-preview framing; the cone then also gets shown, or explicitly excluded per S3's table).

## 2. Path coverage

Specced: fires on first premium Guardian view · replay via "?" + More row. **Everything else is missing:**

- **GAP P1 — no skip/exit.** A 6-step *mandatory-feeling* interactive tutorial at the exact moment someone just paid is a churn risk. Skip must be specced: visible, calm, non-shaming, on every step.
- **GAP P2 — no interrupt/resume.** App backgrounded or killed mid-tutorial (a sandboxed overlay world) → relaunch where? **REC:** persist a step index; on re-entry offer "pick up where you left off / restart / skip." Cheap, and the difference between premium and fragile.
- **GAP P3 — first-fire timing un-examined.** "Fires on first premium Guardian view" = possibly *instantly* after purchase, hijacking the just-paid user before they see THEIR Guardian. **REC:** decide the beat order (recommended: let the real card render + settle one beat, then a non-modal invitation — "want the 2-minute tour?" — rather than an auto-takeover; auto-fire at most once, invitation persists via "?").
- **GAP P4 — replay semantics.** Does "?" restart at step 1 always? Does completing mark `hasSeenGuardianTutorial` (and is that flag in the backup/restore export so a restored device doesn't re-fire)? Un-specced. **REC:** replay always starts clean; seen-flag persisted + exported.
- **GAP P5 — demo-mode exit + confusion-proofing.** The existing `demoStore()` sets `isDemoMode` + `onboardingComplete` and drops into tabs. The bounded showcase spec covers *isolation* (no calibration/`genuineCycleCount` feed) but not the **human paths**: a persistent "Demo" indicator on every surface; the exit ("use my real numbers") path and what it wipes; a user who starts *editing* demo data; kill-and-relaunch while in demo (stays in demo? must be an explicit, escapable state). **REC:** spec all four; the indicator is non-negotiable (mistaking demo for real data is a trust-killer in a finance app).
- **GAP P6 — (A)/(B)/(C)/onboarding sequencing.** Coach-marks firing during the tutorial, or the tutorial invitation colliding with onboarding's last step / the payday-capture sheet / an ack card — none specced. **REC:** one global "discovery arbiter" rule: onboarding > payday capture > tutorial invitation > coach-marks; at most ONE discovery surface per session; nothing fires while any sheet/celebration is up (the VIS-4 ack-density coordinator is the precedent — extend it, don't build a second).

## 3. The tutorial/demo as PREMIUM artifacts

- **GAP B1 — no visual/motion spec for the overlay layer.** "(C) on-brand, calm" is a goal, not a spec. Coach-marks default to the cheap genre (dim + white tooltip + arrow). **REC:** pin the ingredients that already exist: `SheetScrim` blur material for any dimming · `theme/motion` tokens for all transitions · house typography · a spotlight cutout shape consistent with card radii. One shared `DiscoveryOverlay` primitive for (A)'s step frames and (C)'s marks so they're provably one system.
- **GAP B2 — motion register per step unassigned.** Per [[feedback_match_motion_to_surface_job]]: the re-plan-live response = **calm tonal** (it's a data read); the reserve *absorb* and the tutorial *completion* = journey **beats** (a restrained celebration-grade moment is earned). Un-specced → risk of uniformly flat (reads cheap) or uniformly confetti'd (reads gimmicky). **REC:** add a register column to the step list.
- **GAP B3 — both-theme verify only covers (A).** (A)'s decomposition ends "copy + both-theme + a11y verify"; (B) and (C) carry no verify line. The demo is the **App Store's face** (GTM/ASO, screenshots are captured dark per convention but light must be equal per [[feedback_light_mode_equal_premium]]). **REC:** every one of (A)/(B)/(C) gets its own both-theme screenshot verify; the demo additionally gets a "would I screenshot this for the store?" design pass as an explicit exit criterion.
- **GAP B4 — tutorial must drive the REAL components.** The premium difference between "interactive walkthrough" and "slideshow about the app" is whether the sandbox renders the actual `PaydayGuardianCard`/bar/recovery components with scripted data, not mockups. The shared-substrate design implies this; the spec should state it as a hard rule (also guarantees the tutorial inherits every future Guardian polish for free).

## 4. Accessibility of an INTERACTIVE tutorial — the biggest miss

The codebase's a11y method is genuinely good (`utils/a11y.ts`: WCAG 2.2 AA · `groupLabel` one-utterance · `announce` · `decorative`; 21 files reduce-motion-aware). **The 3.5 spec inherits none of it explicitly — "a11y verify" is the entire provision.** Every flagship tutorial interaction is in the class VoiceOver cannot operate without dedicated work:

- **GAP A1 — the floor-drag slider is not VO-operable as specced.** A pan gesture is invisible to VoiceOver/Switch Control. **REC (hard requirement):** the slider gets `accessibilityRole: 'adjustable'` + `increment`/`decrement` actions moving the floor in sensible steps, and every adjustment **announces the outcome** ("Floor $250 — still clear" / "Floor $400 — now tight"), because "watch it re-plan live" is visual-only feedback.
- **GAP A2 — tap-the-zones must be discrete focusable elements.** Bar zones as regions of one Skia canvas = a single opaque blob to VO. **REC:** each zone is (or is overlaid by) a focusable element with a `groupLabel` and a revealed-state announcement; reveal state exposed via `accessibilityState`.
- **GAP A3 — "surprise lands → watch it absorb" is animation-only meaning.** **REC:** every scripted event in tutorial AND demo pairs its animation with an `announce()` of what just happened. Rule of thumb to put in the spec: *no tutorial state change may be conveyed by motion alone.*
- **GAP A4 — reduce-motion variants unspecced.** Live re-plan, absorb/release, coach-mark pulse/spotlight — each needs a reduced variant (cross-fade + announcement) that still conveys the change. Precedent exists in 21 files; the spec must mandate it for all three features, and the e2e gate should include a reduced-motion run of the tutorial path.
- **GAP A5 — Dynamic Type on overlays.** Coach-mark bubbles and step copy are the classic clip sites, and spotlight-position math breaks when the target reflows at XXL sizes. **REC:** spec max-size verify for every bubble/step frame (the FormSheet `numberOfLines` lesson from the closeout applies here verbatim).
- **GAP A6 — coach-marks under VoiceOver.** A spotlight is meaningless to a non-sighted user, and an un-focusable floating bubble is a trap. **REC:** on mark appear → announce + focusable bubble + reachable dismiss; the spotlighted control stays reachable; AND decide whether visual coach-marks fire at all when VO is running (recommended: suppress the spotlight, keep the announced hint — the More replay row is the accessible discovery home).
- **GAP A7 — completion parity as an exit gate.** **REC (the one-line fix for all of the above):** add to 3.5's exit criteria: *"a VoiceOver user can complete every tutorial step end-to-end, and a Switch-Control/keyboard user likewise (iPad ⌘/web)"* — this also forces programmatic operability, which is exactly what makes the tutorial e2e-testable in the web gate. A11y and testability are the same work here; spec them together.

## 5. Coach-marks (C) — completeness

Specced: calm · one-at-a-time · dismissible · replayable · iOS-16-safe · Android-reusable · targets = long-press menu + widget/Lock-Screen nudges. Gaps:

- **GAP C1 — target list is incomplete.** Hidden-by-design surfaces shipped in Phase 3 with zero visible affordance: **swipe-to-delete** on all four row types (3.4.4) · **trajectory touch-scrub** + waypoints (3.4.1) · **Cash-Runway drag-select** (3.4.2) · **"Log payment"** — which will live INSIDE the already-invisible long-press menu (3.5.5.2: double-hidden, the strongest candidate after the menu itself) · **Siri/Shortcuts existence** (voice features are undiscoverable by definition; one nudge or a More row) · the **Live Activity toggle** (premium payday countdown buried in Preferences). **REC:** triage this full list explicitly (mark each: coach-mark / More-row mention / deliberately-undiscovered-is-fine); don't let "priority target" quietly become "only target."
- **GAP C2 — trigger conditions + pacing unspecced.** When does the widget nudge fire — launch 1 (annoying) or after the Nth session/first payday (earned)? Max marks per session? **REC:** per-mark trigger table + a global cap (≤1/session), all routed through the P6 arbiter.
- **GAP C3 — replay home unspecced.** "Replayable" — from where? **REC:** a "Reset tips" action co-located with the "How the Guardian works" row in More (one discovery home).
- **GAP C4 — persistence schema.** Per-mark seen/dismissed flags, in the store, exported in backup. Un-specced; cheap; spec it.
- **GAP C5 — don't-fight-gestures is a known live hazard, not a platitude.** Two shipped lessons apply directly: touchables inside a `GestureDetector` don't get taps on device ([[feedback_gesturedetector_swallows_taps]], re-confirmed by the 3.5.0 headerAction bug), and marks target rows that own pan/long-press gestures. **REC:** spec that mark overlays render in a sibling layer OUTSIDE all gesture handlers, and that the long-press mark *invites* the gesture rather than intercepting it; device-verify tap-through on the Phase-6 pass.

## 6. Recommended spec additions (consolidated)

1. **A11y-operability block (A1–A7)** added to the (A) spec + the exit-gate line "VO user completes the tutorial end-to-end"; reduce-motion + Dynamic-Type + announce-not-motion rules named per step. *(Biggest miss; also buys e2e-testability.)*
2. **State coverage table** (S1–S3): sandbox tuned so the floor-drag crosses clear→tight→at-risk; a Recovery step (or explicit contextual-first-shortfall alternative); explicit taught/contextual/excluded status for every RS.6 state.
3. **Path spec** (P1–P6): skip on every step · resume-or-restart · invitation-not-hijack first fire · seen-flag persisted+exported · demo indicator/exit/edit/relaunch semantics · one discovery arbiter across onboarding/(A)/(C).
4. **Free-tier "?" decision (S4):** recommended — free can run the tutorial as the value-led taste; free-at-risk showcase entry point pinned.
5. **Premium-bar spec (B1–B4):** shared `DiscoveryOverlay` primitive on `SheetScrim`+motion tokens · per-step motion register (calm read / beat moments) · both-theme verify for ALL of (A)/(B)/(C) · hard rule: sandbox drives the real components.
6. **Coach-mark completion (C1–C5):** full hidden-surface triage table · per-mark triggers + session cap · "Reset tips" home · persisted flags · marks outside gesture handlers (device-verified).
