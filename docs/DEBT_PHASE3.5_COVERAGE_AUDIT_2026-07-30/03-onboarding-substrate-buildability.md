# Lens 3 — Onboarding coherence · demo isolation · sandboxed-substrate buildability

> Phase 3.5 pre-build coverage audit, 2026-07-30. Auditor lens: coherence with the existing onboarding/discovery surfaces + whether the shared sandboxed scriptable Guardian substrate is fully specced and buildable. Verified against the CURRENT code (not the plan's premises).

**VERDICT: NOT BUILD-READY as specced — the architecture is favorable (pure selectors + pure `applyRollover` + a per-store-instance sync design make an isolated sandbox genuinely cheap), but the spec has two blocker-class holes (the intro-absorption/trigger matrix is undefined, and `isDemoMode` is NOT the isolation the spec assumes — it's demo-data-in-the-REAL-store, contradicting (B)'s cold-start bound), plus a signal-with-no-producer: the tutorial's "watch it absorb / watch it release" beats are only produced at a ROLLOVER boundary, which the step list doesn't script.**

---

## 1. Onboarding coherence — the trigger matrix is unspecced

**What exists today (verified in code):**
- **First-run onboarding** (`apps/rn/src/app/onboarding.tsx`): Welcome → Paycheck → FirstDebt/Bill → Completion. Free-tier, teaches nothing about the Guardian. Welcome offers "Try with Sample Data" → `importStore(demoStore())`.
- **Guardian intro (2.4.11.3)** (`apps/rn/src/components/plan/PaydayGuardianCard.tsx:105–123`, wired `app/(tabs)/index.tsx:228–229`): a passive inline dismissible text block, gated `isPremium && !prefs.guardianIntroSeen`. One flag: `prefs.guardianIntroSeen` (`data/models.ts:82`, migration-backfilled `false`).
- **VIS-4 ack coordinator** (`app/(tabs)/index.tsx:141`): Today shows at most ONE acknowledgment card at a time, ranked. Shipped (the closeout audit's must-fix — confirmed in code + `ack-coordinator.spec.ts`).

**Gaps:**

- **GAP 3.1 (BLOCKER) — "absorbs/upgrades the 2.4.11.3 intro" has no flag semantics.** Reuse `guardianIntroSeen` or add a new `guardianTourSeen`? Each choice fails a cohort if undecided:
  - Reuse the flag → any user who already dismissed the intro (Jason's device, TestFlight testers, any store where it's `true`) NEVER sees the tutorial.
  - New flag, auto-fire → intro-seen users get taught TWICE (intro then tutorial), and the dead intro code/flag needs an explicit retirement decision (keep the flag for migration honesty, remove the render path).
  - The user matrix the spec must state: **new free** (sees onboarding only — tutorial never fires; intended?) · **new premium** (buys when? the paywall is post-onboarding, so "first premium Guardian view" = first Today render after purchase) · **mid-journey upgrader** (backfill `false` → fires — with what priority vs. that render's other acks?) · **intro-already-seen premium** (undefined — the double-teach/never-teach fork above).
- **GAP 3.2 (BLOCKER) — auto-fire collides with the VIS-4 single-ack-slot contract.** The intro is a passive inline block; the tutorial is a takeover flow. First-premium-view on Today can simultaneously hold: payday capture sheet, a pending milestone ack, reserve-release/walkback acks, the trial-conversion card — VIS-4 exists precisely to stop this stacking. The tutorial's auto-fire must be **registered in that same priority order** (and probably ranked above acks but below the payday capture sheet — an actual money moment beats a lesson). Spec is silent. Also silent: **"Not now" / interrupted mid-tutorial** → does it re-offer, and where does the pending state live?
- **GAP 3.3 — free users see NO Guardian teaching at all.** Tutorial fires on first *premium* view; onboarding doesn't cover the Guardian; the free card shows the real read + invite (`PaydayGuardianCard.tsx:230–234`). A sandboxed tutorial is arguably the best *pre-paywall pitch* the app could have (it demos the actor honestly, per [[feedback_premium_gating_value_led]]) — but whether "?"/More replay is free-reachable is undecided in the spec. Decide (recommend: yes, free-reachable).
- **GAP 3.4 — (C) coach-marks join the same arbitration.** Coach-marks + tutorial + intro + acks all target the same first sessions. Without one declared order, the first premium render can stack three teaching surfaces. Fold (C)'s trigger rules into the same priority spec as GAP 3.2.

## 2. Reachability / replay

- **GAP 3.5 — neither replay entry point exists yet; both are cheap but unspecced.** No "?" affordance on the card head (`PaydayGuardianCard.tsx:141–149`); no "How the Guardian works" row in More (`app/more.tsx` — natural home: the reflective block near History, or Preferences). Fine as net-new work, but the spec should name: (a) the "?" shows in ALL card states incl. free/stale (it opens a sandbox, so state doesn't matter); (b) replay **constructs a fresh sandbox every launch** — with the §3-substrate below, replay from a real mid-journey/shortfall state touches zero real data by construction. No further mechanism needed — but only if the substrate is built as §3 says, not on `isDemoMode`.
- **Replay + premium gating:** if free-reachable (GAP 3.3), the tutorial IS a premium demo — (A) and (B) then overlap almost entirely ("the interactive demo is essentially a scripted run of the tutorial", per the plan). Good — one build, two entries. The spec should say this out loud so (B) isn't built as a second flow.

## 3. Demo-mode isolation — `isDemoMode` is the WRONG primitive, and the spec conflates two demos

**What exists today (verified):** `demoSeed.ts` **REPLACES the real store** via `importStore(demoStore())` — persisted to the real blob, `prefs.isDemoMode: true`. The ONLY thing `isDemoMode` disables is the payday capture sheet (`hooks/use-payday-capture.ts:45`). Everything else treats demo data as real:

- **Widget/Siri leak:** `startWidgetSync` (`widget/widgetSync.ts`, started in `_layout.tsx`) mirrors the store to the App-Group snapshot with **no demo gate** → the home-screen widget, Lock Screen, and the 3.5.5 Siri queries would all speak the demo debts.
- **Notification leak:** `useNotificationSync` has **no demo gate** → demo bills schedule real reminders; a premium at-risk demo state arms a real §2.8 risk push (mitigated today only by `notificationsEnabled` defaulting `false` and the demo store being free-tier — both accidents, not contracts).
- **Live Activity leak:** `paydayLiveActivityEnabled` defaults **true** (`defaults.ts:50`) — a premium demo state starts a real payday-countdown Live Activity on fake dates.
- **No exit:** once in demo mode, More offers only "Delete all data". A GTM showcase needs a one-tap "Start fresh with my numbers".

**GAP 3.6 (BLOCKER) — 3.5's sandbox must NOT reuse `isDemoMode`; it needs the ephemeral-second-store contract, which the architecture already supports but the spec never states.** The good news the builder must be told: `selectPaydayGuardian` and every Guardian selector are **pure `DebtStore → brief`** (`guardianSelectors.ts:454`); `applyCapture`/`applyRollover` are **pure store→store** (RS.3-tested); persistence, widget sync (WeakSet-keyed per store instance, only ever started on `appStore`), and notification sync bind ONLY to `appStore`. So a second in-memory store instance (or even a plain `DebtStore` object + pure selectors) is isolated from persistence/widget/notifications/Siri/calibration **by construction** — no flag needed, nothing to disable. If the spec doesn't say this, the path of least resistance is `importStore` + `isDemoMode`, which inherits every leak above.
- **Real-calibration isolation** (`genuineCycleCount` / `cycleHistory` / `incomeActualsLog`): automatic under the second-store contract — the producers (`substrateProducers.ts`) only run inside whatever store's actions invoke them. The one rule to write down: **the sandbox store is never handed to `appStore.importStore`, never persisted, never passed to `startWidgetSync`.**
- **Reverse leak (real → sandbox):** the tutorial must be a fabricated example, never seeded from the user's real numbers (a user in a real shortfall shouldn't see their own crisis re-enacted as a lesson). State it.
- **"Reserves HELD not deployed" enforceability:** yes — trivially. `deriveConfidenceContext` (`guardianPredictionCore.ts:33–45`) holds the reserve whenever `genuineCycleCount < DISCOVERY_CYCLES (3)`; a sandbox seeded at `genuineCycleCount: 0–1` is *structurally incapable* of showing a matured Guardian. The bound enforces itself — IF the sandbox is seeded cold.

**GAP 3.7 — the existing `demoStore()` CONTRADICTS (B) and the spec doesn't reconcile them.** `demoSeed.ts:67` fabricates `genuineCycleCount: 6` + 6 cycles of history — the exact "matured Guardian the month-one buyer can't be" that (B) forbids (its own comment defers the cold-start demo to 2.4.11 = now). Undefined: does (B) **replace** demoSeed, **coexist** (mid-journey free explore vs. cold-start premium showcase are different jobs), or does demoSeed's Guardian-facing state get re-bounded? Two demo states with different honesty rules and no decision = a mid-build wall.

## 4. The scriptable substrate — one signal-with-no-producer class, one hard-wire

- **GAP 3.8 (BLOCKER-adjacent) — "watch it absorb" / "watch it release" have no IN-CYCLE producer.** The convergence-audit class, present here:
  - *Absorb:* `recordSurpriseOutflow` logs the outflow + walks back attestation — but the **visible** "the reserve covered it" acknowledgment (`pendingReserveRelease.tapped/covered`, `models.ts:184–188`) is produced **only at a rollover** (the `priorReserveHeld` held→free transition in `payday.ts`). Mid-cycle, the shipped card has no absorb visual.
  - *Release:* likewise — `genuineCycleCount` crossing `DISCOVERY_CYCLES = 3` at a rollover.
  - **Fix (cheap, but must be scripted):** `applyRollover` is pure, so the sandbox can deterministically script **"the next payday arrives" beats** — seed `genuineCycleCount: 2`, surprise lands, roll → tapped-release ack renders; that IS the absorb+release story. The tutorial step list must be rewritten to include these explicit time-advance beats; as written ("tap → watch it absorb") it implies an immediate visual that would be **net-new design scope** — choose consciously, don't discover it mid-build.
- **GAP 3.9 — `CushionFloorSheet` hard-writes the REAL store.** `CushionFloorSheet.tsx:26` → `appStore.getState().setCushionFloor(value)`, and the sheet is mounted *inside* `PaydayGuardianCard` (line 291). The "drag the floor → live re-plan" step, if built by reusing the card, mutates the user's real `cushionFloor`. Everything else on the card is prop-injected (verified — this is the only `appStore` reach-in among the card's children). **Fix:** lift to an `onSetFloor` prop (defaulting to the appStore write) or a store-instance prop, BEFORE the tutorial build.
- **GAP 3.10 — tap-to-reveal bar zones are net-new interaction.** `CushionBarCanvas` is a Skia canvas, `accessibilityElementsHidden` (`PaydayGuardianCard.tsx:152–156`). "Tap each zone to reveal" needs a hit-target overlay layer (with a11y-visible targets) that doesn't exist — reuse of the bar is a *render* reuse, not an *interaction* reuse. Budget it.
- **Determinism (mostly fine, two pins to write down):** dates should be fabricated relative to a **frozen "today"** at sandbox creation (the `demoSeed` `todayLocalISO()+offsets` pattern); pin `inputsAsOf = currentDate` in every sandbox state or the §2.0.d stale-advisory dims the bar mid-lesson (an accidental wrong lesson). The floor slider must mirror `setCushionFloor`'s real clamp (snap-$25 / cap-$1000 / NaN→200, RS.3-verified) so the sandbox never behaves differently from the real control it's teaching.
- **No-producer sweep of the remaining steps (clean):** "meet it" (any seeded state) · bar zones (brief fields) · floor drag (pure re-select) · safe move / "your call" (`brief.safeMove` + the standing caption) · free at-risk showcase (`subscriptionPlan:'free'` + a shortfall seed → the state-aware invite, `PaydayGuardianCard.tsx:95–98`) — all producible from a seeded store + pure selectors. Only absorb/release (GAP 3.8) crosses the rollover boundary.

## 5. Coach-marks (C) — infra + platform gates

- **GAP 3.11 — zero coach-mark/tutorial infra exists** (grep `coachmark|tutorial|walkthrough` over `src/` is clean). Greenfield: anchor/measure system + seen-flags. Seen-flags land in `prefs` → **migration** (additive-optional like `cycleTopUp`, or a version bump — decide; additive-optional is the established cheap pattern).
- **GAP 3.12 — the priority coach-mark targets an iOS-ONLY gesture.** The long-press context menu is real only on iOS (`RowContextMenu.tsx` base = transparent passthrough on web/Android; `RowContextMenu.ios.tsx` is the implementation). The coach-mark must be platform-gated or web/Android users (and the web e2e gate) get a mark pointing at a gesture that doesn't exist. Same for "add the widget / Lock Screen" nudges (native-iOS-only). Consequence: **the coach-mark layer is web-e2e-testable only in its scaffolding, not its priority content** — plan the verify step accordingly (sim/device, per the Maestro half of the gate).

## Recommended additions (fold into the 3.5 spec before build)

1. **Write the substrate contract as its own numbered sub-item, first in the build order:** `createSandboxStore(scenario)` = a second store instance (or plain `DebtStore` + pure selectors), frozen base date, `inputsAsOf` pinned, seeded `genuineCycleCount ≤ 1`; scripted transitions = pure `applyRollover`/`applyCapture`/floor-set on the sandbox; **never** `importStore`d, persisted, or widget-synced; never seeded from real data. `isDemoMode` is explicitly NOT this feature's isolation mechanism.
2. **Decide the trigger matrix pre-build (this is a Jason design decision, per the standing "align design-shaped work first"):** recommend — new `guardianTourSeen` flag; the 2.4.11.3 inline intro render path retires; intro-already-seen users get a quiet "Take the tour" chip (no auto-takeover); auto-fire registers in the VIS-4 priority order (below the payday capture sheet, above celebration acks); "Not now" re-offers via the "?" entry only. "?" + More row are free-reachable (the tutorial doubles as the honest premium pitch).
3. **Rewrite the tutorial step list with explicit "next payday arrives" beats** for absorb + release (rollover-produced signals), OR consciously scope a new immediate absorb visual as design work — don't let the builder discover the missing producer mid-build.
4. **Pre-build refactor ticket:** lift `CushionFloorSheet`'s `setCushionFloor` write to a prop (the only real-store hard-wire in the card's tree — verified).
5. **Reconcile (B) with `demoStore()`:** recommend (B) is a *scripted sandbox run* (shared with the tutorial) reachable from Welcome/paywall, `demoStore()` keeps the whole-app-explore job but its Guardian-facing fields get re-bounded to cold-start honesty (`genuineCycleCount ≤ 1`, drop the fabricated 6-cycle track record's Guardian implications) — and add a **"Start fresh with my numbers" demo-exit** row (shows only when `isDemoMode`), which the GTM showcase needs regardless.
6. **Platform-gate (C):** long-press + widget/Lock-Screen coach-marks iOS-only; coach-mark seen-flags as additive-optional prefs; note the verify split (scaffold on web e2e, content on sim/device).
